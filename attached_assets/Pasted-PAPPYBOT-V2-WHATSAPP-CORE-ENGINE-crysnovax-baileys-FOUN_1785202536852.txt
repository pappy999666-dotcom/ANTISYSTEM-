PAPPYBOT V2 — WHATSAPP CORE ENGINE & @crysnovax/baileys FOUNDATION (PROMPT 2)

You are continuing the development of PAPPYBOT V2. Prompt 1 has already been completed and provides the project architecture. In this prompt, implement only the WhatsApp core engine using @crysnovax/baileys. Do not implement the anti-system, Telegram panel, web dashboard, or AI assistant yet.

Library Requirements

- Use @crysnovax/baileys exclusively.
- Before implementing any feature, verify that it is supported by the library. Do not invent unsupported APIs or fake behavior.
- Follow the library's recommended connection lifecycle and message formats.
- Keep the implementation modular so future prompts can plug into it cleanly.

---

OBJECTIVE

Build a production-grade WhatsApp session engine capable of managing multiple independent WhatsApp accounts with complete isolation.

The engine must be:

- lightweight
- asynchronous
- scalable
- restart-safe
- memory efficient
- event-driven
- production-ready

---

MULTI SESSION ARCHITECTURE

Every paired WhatsApp account is its own isolated workspace.

Each session must maintain:

- Authentication state
- Socket instance
- Runtime cache
- Event listeners
- Group cache
- Contact cache
- Scheduler
- Configuration
- Permission state

No session should ever affect another.

---

SOCKET MANAGER

Create a centralized Socket Manager responsible for:

- Creating sockets
- Destroying sockets
- Reconnecting sockets
- Session lookup
- Runtime health checks
- Listener attachment
- Resource cleanup

The Socket Manager must prevent duplicate sockets and duplicate listeners.

---

AUTHENTICATION

Support all authentication methods provided by the library.

Requirements:

- Pairing code flow
- QR code flow
- Multi-file authentication storage (or the library's recommended persistent auth method)
- Session restoration after restart
- Automatic reconnection when appropriate
- Clean logout handling

When a session logs out permanently, purge only that session's runtime resources without affecting other sessions.

---

CONNECTION LIFECYCLE

Handle every connection state exposed by the library.

Examples include:

- connecting
- connected
- disconnected
- reconnecting
- logged out
- stream replaced
- connection closed
- retry required
- restart required

For every state:

- emit an internal event
- update runtime status
- notify dependent services
- clean resources if necessary

Avoid infinite reconnect loops.

---

ERROR HANDLING

Gracefully handle library errors such as:

- authentication failures
- invalid session state
- bad MAC or corrupted session data (when surfaced by the library)
- network interruptions
- temporary server failures
- socket closure

Errors should be logged and surfaced without crashing the application.

---

CLIENT CONFIGURATION

Use the library's supported client/browser configuration.

If the library allows selecting a supported Android or iOS client profile, expose it as a configurable option.

Do not attempt to spoof unsupported identities, bypass platform protections, or claim to evade WhatsApp detection. Only use documented, supported configuration exposed by the library.
